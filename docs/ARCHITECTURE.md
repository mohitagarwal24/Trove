# Architecture

One Next.js application and a PostgreSQL database serve browser, JSON API and MCP clients. Shared services under `src/server` own authorization and business rules. Render Free runs the web app and an embedded queue drain; local development can use a standalone worker. There is no paid hosted worker or filesystem dependency.

## Source to delivery

1. An allowlisted importer fetches real FDA records, normalizes whitelisted fields, validates dates and encrypts an immutable `DatasetSnapshot`. Provider uploads use the same storage contract. Public offers expose metadata and a fixed two-row/four-field preview only.
2. An external agent submits category-specific requirements through `discover_data`, the browser submits explicit requirements, or optional Gemini interprets a browser brief. Trove’s shared evaluator searches public metadata with PostgreSQL full-text ranking, checks matching private-row counts, fields, permitted use, freshness, ownership and budget, then selects complete lowest-cost coverage or returns gaps. It never silently relaxes a request. No external-agent call needs a Trove model key. Missing browser AI configuration/quota produces an explicit error and an action to choose requirements; it never silently substitutes an interpretation.
3. A quote pins source/version/hash, selected record indexes and fields, purpose, licence, freshness, delivery-cache hours, commission and exact USD total. It expires after five minutes. Provider edits create new versions and cannot mutate existing quotes.
4. Purchase creation serializes acquisitions by workspace, rejects already-owned or pending duplicate scopes, locks the quote and task budget, reserves only the exact total, and persists an idempotency key. The browser obtains genuine PayPal buyer approval. MCP cannot approve, capture or alter recipients.
5. The worker authorizes the order, prepares every approved dataset and validates the complete bundle before capture. Prepared results are encrypted. Authoritative completed capture then creates the entitlement, receipt, balanced ledger and seller payables in one transaction.
6. Reconciliation uses persisted payment identities after uncertain responses. It never retries a charge with a new identity. Refund completion revokes further access and reverses accounting. Submitted/paid payouts are flagged for separate recovery.

## Identity and isolation

Email/password or Google OpenID Connect registration creates a private user and workspace. Password accounts remain restricted until email ownership is proven. Six-digit codes are cryptographically random, keyed-hashed with a distinct domain and random nonce, browser-session-bound, valid for ten minutes and five attempts, and serialized per user for one-time consumption. Resends and guesses have separate shared hourly limits. Confirmation revokes pending sessions and tokens before issuing a new session. The browser can resume the pending step; API and MCP authentication reject unverified identities, including legacy agent tokens. Missing Gmail configuration or delivery errors never skip verification. Expired challenges are purged by maintenance.

Google uses PKCE, browser-bound single-use state, nonce and Google’s signed ID-token verification. Its verified matching email does not need a separate code. Existing email accounts require explicit authenticated linking; no automatic email-based account merge occurs. Google-only account closure requires a recent Google session. Scrypt passwords, hashed expiring session/agent tokens, cookie Origin checks, browser-only account/provider actions, atomic database rate limits and server ownership checks protect each boundary. Password recovery uses single-use hashed tokens and genuine HTTPS email; a successful reset also verifies ownership of that email and clears pending codes. Password change/reset revokes sessions, agent tokens and OAuth grants, and deletes outstanding authorization codes. Account closure disables access, redacts profile details and retains accounting identities. See [credential setup](GOOGLE_AUTH_SETUP.md).

Provider onboarding is pending until an operator reviews identity, rights and payment routing. Public clients cannot self-approve or change payout recipients. Uploaded data remains encrypted and unlisted while pending. Declared publishing rights require actual operator review; a checkbox cannot prove a legal entitlement.

## Agent authorization

Remote MCP uses Trove account OAuth with RFC 9728 discovery, dynamic client registration and PKCE S256. Single-use hashed codes bind client, exact callback, user, workspace, scopes and MCP audience. One-hour access tokens and 30-day rotating refresh families are stored only as hashes. Refresh reuse revokes the family transactionally; membership and verified-account access are rechecked. OAuth access tokens cannot be used against unrelated JSON API resources. Browser-only consent and disconnection enforce Origin and ownership; account security changes revoke all grants. Client-provided names are labelled rather than presented as verified identities. A stable authenticated `get_profile` supports client account identification. Advanced manual tokens and the database-free stdio bridge remain compatible. See [agent setup and protocol](AGENT_CONNECTIONS.md).

Successful MCP tool completion updates nullable `AgentToken.lastUsedAt` and `lastTool` metadata, scoped to the authenticated active token. Failed tools do not advance it. This best-effort metadata write cannot turn a completed business operation into an error. Connected-app listings aggregate the latest successful token activity; prompts, results and secrets are not logged. The additive migration preserves existing credentials.

## Research and owned-data views

Discovery stores a coverage summary on requirements JSON and structured source decisions: required/missing fields, requested/available record counts, source dates, acquisition status and minimum complete price. Resume uses the stored explanation. Comparisons are invalidated by meaningful scope or cap changes, independent of JSON key ordering. `/workspace?from=<task-id>` loads an owned task through the existing ownership boundary and copies only its scope into a draft. It creates no task, quote or payment until explicitly submitted.

`GET /api/library` searches metadata of captured, unrevoked entitlements in the current workspace/payment environment with keyset pagination. It does not expose private rows, and cache expiry does not remove ownership. Version notices compare the original purchased snapshot with the actual current active offer; a newer version is not by itself grounds for charging again.

`GET /api/purchases/<id>/evidence` uses the existing authorised result retrieval/restoration service, then checks the captured entitlement again. The no-store export includes original rows, scope, provenance/checks, receipt/payment references, canonical SHA-256 batch and record fingerprints. Reused sources are references to their original purchases, not automatically joined payloads. `scripts/verify-evidence.mjs` recomputes the content fingerprints without dependencies. It checks internal consistency rather than publisher identity, a digital signature or PayPal settlement. Refunds prevent future retrieval but cannot recall downloaded copies.

## Durable operations

PostgreSQL is authoritative for jobs, leases, budgets and financial state. Embedded timers improve latency only. Verified webhooks are persisted uniquely with an outbox job before acknowledgement; jobs reconcile external resources rather than applying event labels blindly. Protected hourly maintenance recovers work after restarts, imports sources daily and purges expired terminal results. Health checks never query the database.

Payment, fulfilment and settlement are separate states. Sandbox and live environments cannot operate on each other's purchases. Encrypted delivery caches default to 24 hours, pinned in the quote. Unrefunded purchase entitlements durably cover the original provider, canonical batch content, purpose, licence, fields and scoped record occurrences. Row/key reordering, retrieval dates and price-only changes do not invalidate ownership; changes to purchased values or expanded scope require a new quote. Only requested fields and record occurrences participate in the comparison: edits to other rows or columns do not invalidate an unchanged purchased subset. Duplicate occurrences are counted, so ownership of one identical row does not grant two. Cache expiry rebuilds the approved source subset without payment or ledger writes. Ownership derives from retained captured purchases and source snapshots, including historic purchases, rather than an agent’s memory. Mixed plans list reused sources separately; all-owned plans have zero total and cannot enter checkout. Separate prior purchases are not combined to invent a broader scope. Source snapshots and financial history are retained to preserve previously approved versions. Optional Elasticsearch contains public metadata only; database filtering rechecks visibility and current availability.

## Practical limits

Free hosting can sleep and scheduled jobs can be delayed. No uptime guarantee is implied. There is no stored wallet balance, escrow, reusable spending mandate or automatic split checkout. Live marketplace operation still requires merchant approval, provider contracts and operational policies. The current integration defaults to PayPal Sandbox; enabling live mode is an explicit configuration and business decision.
