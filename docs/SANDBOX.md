# Credentialed PayPal sandbox verification

Not yet performed: no credentials were supplied. Complete this runbook before claiming the external payment acceptance criteria.

1. Create a PayPal Developer account and a REST application attached to the Trove sandbox business account. Record its client ID, secret and merchant ID in the server environment. Create one personal buyer and at least two seller recipient sandbox accounts. Do not use personal real-account passwords as API credentials.
2. Configure `APP_URL` to the actual origin. Create a webhook for this application at `/api/webhooks/paypal`. Set `PAYPAL_WEBHOOK_ID`; subscribe to checkout approval, authorisation, capture, refund and payout events used by the application. A publicly reachable HTTPS endpoint is needed to validate actual webhook delivery.
3. Start web and worker. Run `npm run check:integrations`. This checks configuration and database/search; it does not establish payment success.
4. Prepare a fresh one-source quote in the buyer workspace. Continue to sandbox checkout. The v6 SDK uses client-ID authentication, explicit eligibility and a payment session. Approve using the personal sandbox buyer. The browser calls Trove's approval endpoint; it never establishes capture success itself.
5. Verify actual order, authorisation and completed capture IDs against the sandbox dashboard/API. Check exact amount, USD, merchant and plan binding. Confirm a result entitlement, balanced capture ledger and payable are created once. Repeat result retrieval and replay the completed event: no extra charge or payable.
6. Test a two-seller bundle. Make one adapter fail in an isolated development test environment. Verify no capture, a confirmed void, no accessible staged data, no seller payable and released task reservation. Never label a void as a refund.
7. Simulate capture transport uncertainty using the controlled integration test. For credentialed validation, capture then interrupt the worker before finalization and restart it. Verify reconciliation returns the completed resource and delivers once. Do not issue a new capture identity to resolve an uncertain existing capture.
8. Request a refund for a concrete captured sandbox purchase with a reason. Wait for an authoritative completed refund. Verify receipt status, entitlement revocation and stopped unpaid settlement. A previously submitted/paid payout requires separate recovery.
9. Enable Payouts only after confirming account access. Fund the sandbox business balance sufficiently, including fees. Set each seller's sandbox recipient email. Run the worker and inspect both batch and item status. Only a successful item means seller paid. Pending, unclaimed, failed and returned states must remain visible. Keep stable sender batch/item identities for retries.
10. Verify a real signed webhook. Missing/forged signatures must be rejected. Persist a unique verified event and its job before acknowledging. Replay the event and deliver events out of order; reconcile authoritative resources rather than blindly applying status labels.

PayPal API access, funding availability, settlement approval and country support must be checked separately before production. This sandbox collect-and-payout demonstration is not a wallet, escrow, credit facility, stored-payment mandate or approved production marketplace arrangement.

Capture uncertainty retains reservations. Jobs retry with bounded backoff and eventually expose failure for review; capture mutations stop after the automated retry window. AES-GCM staging is retained for recovery while payment is uncertain. Paid access expires at the configured deadline; expired ciphertext for terminal purchases is purged.
